# Эксплуатация CRM: уведомления, резервные копии, мониторинг, аналитика

Документ для администратора сайта ООО «Интегро». Секреты (ключи, токены, пароли) задаются только в
переменных окружения сервера (панель Timeweb Apps → «Переменные»). В репозиторий, журналы и браузер они не попадают.

## 1. Уведомления

### События

| Тип | Когда создаётся | Ключ против дублей |
| --- | --- | --- |
| Новое сообщение | клиент написал в MAX или Telegram | одно на диалог за интервал (по умолчанию 15 мин, меняется в настройках) |
| Ждёт ответа | диалог отмечен «нужен ответ»: режим оператора, лимит автоответов, «нужен специалист», ответ «нет» в опросе | одно на событие |
| Заявка с сайта | заявка сохранена в базе | одно на заявку |
| Заявка из бота | заявка оформлена в MAX или Telegram | одно на заявку |
| Ошибка отправки | ответ клиенту не отправлен (ошибка или неизвестный результат) | одно на попытку |
| Ошибка обработки | событие мессенджера не обработано после 5 попыток | одно на событие |
| Сбой резервной копии | ежедневная копия не создана | одно на запуск |

Каждое событие — одна запись в `notifications` (уникальный `dedupe_key`). Доставки по каналам — отдельные
строки в `notification_deliveries`: по одной на каждую push-подписку и каждого получателя в Telegram.

### Центр уведомлений в админке

- Колокольчик в шапке: число непрочитанных, последние 10 уведомлений, переход к объекту. Число
  непрочитанных показывается и в заголовке вкладки.
- Обновление — опросом раз в 20 секунд, пока вкладка видима, и сразу при возврате на вкладку.
- Раздел «Уведомления» (`/admin/uvedomleniya`): список с фильтрами по типу и прочитанности, отметка о
  прочтении (по одному или все сразу).

### Браузерные push-уведомления (Web Push)

1. Сгенерируйте ключи: `npx web-push generate-vapid-keys`.
2. Задайте на сервере `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, при желании `VAPID_SUBJECT`
   (`mailto:…`). Секретный ключ хранится только на сервере.
3. Перезапустите приложение. В «Уведомления → Настройки» нажмите «Включить push-уведомления» и
   разрешите уведомления в браузере. Подписка хранится в базе (`push_subscriptions`).
4. Отключение: кнопка «Отключить на этом устройстве» или отзыв разрешения в браузере. Подписки,
   которые push-сервис считает недействительными (ответ 404/410), удаляются автоматически.

На iPhone push работает только для сайта, добавленного на экран «Домой» (iOS 16.4+), — это ограничение Safari.

### Уведомления в Telegram

Используется тот же бот, что и для клиентов (`TELEGRAM_BOT_TOKEN`).

1. «Уведомления → Настройки → Создать ссылку для подключения»: создаётся одноразовая ссылка, она действует 15 минут.
2. Откройте ссылку в Telegram сотрудника и нажмите «Старт». Бот ответит, что уведомления подключены.
3. Посторонний не может подписаться без действующего кода. В базе хранится только SHA-256 кода, код
   одноразовый. Для такого `/start` карточка клиента не создаётся.
4. Отключить получателя можно в настройках («Отключить»). Если сотрудник заблокировал бота, получатель
   отключается автоматически.

### Что уходит во внешние сервисы

Push-сервисы браузеров (Google, Apple, Mozilla) и Telegram — сторонние сервисы. Поэтому в push и
Telegram уходят только тип события, канал и ссылка в админку. Имени клиента, телефона и текста
сообщения там нет (см. `externalText` в `src/lib/notifications/texts.ts`). Подробности видны только в админке после входа.

### Повторы

Доставка повторяется, только если сообщение точно не ушло: нет соединения, ответ 429 или временная
ошибка сервиса. Интервалы — 1, 5, 15, 60 и 180 минут; заголовок `Retry-After` учитывается. Всего не
больше 5 попыток. Если результат Telegram неизвестен (тайм-аут после отправки), повтора нет, чтобы не
задвоить уведомление. Неуспешные доставки видны в «Системе» с кнопкой «Повторить».

## 2. Резервное копирование

### Как устроено

- **Состав копии.** Логическая копия всех таблиц сайта: заявки, обращения, переписка, уведомления,
  настройки, журналы. В копию не входят сессии администратора, попытки входа и коды привязки.
- **Согласованность и формат.** Выгрузка идёт в одной транзакции `REPEATABLE READ READ ONLY`. Результат —
  gzip, затем шифрование AES-256-GCM ключом `BACKUP_ENCRYPTION_KEY`. Без ключа копию не прочитать.
- **Ежедневная копия.** Делается автоматически в `BACKUP_HOUR_MSK` (по Москве) и отправляется во внешнее
  S3-хранилище (`BACKUP_S3_*`). Копии старше `BACKUP_RETENTION_DAYS` удаляются из хранилища.
- **Ручная копия.** Кнопка «Создать копию в хранилище» в «Системе» (при настроенном S3), не чаще раза в
  5 минут. Кнопка «Скачать зашифрованную копию» отдаёт файл в браузер.
- **Журнал и сбои.** Каждый запуск записывается в журнал копий (`backup_runs`) и виден в «Системе». Если
  копия не создана, приходит уведомление «Сбой резервной копии».

### Настройка

1. Создайте ключ: `openssl rand -hex 32`. Сохраните его в менеджере паролей **отдельно от сервера**.
   Без ключа восстановление невозможно.
2. Создайте бакет в S3-совместимом хранилище (например, объектное хранилище Timeweb Cloud, регион
   Москва). Создайте ключ доступа с правами только на этот бакет.
3. Задайте на сервере `BACKUP_ENCRYPTION_KEY`, `BACKUP_S3_ENDPOINT` (https://…), `BACKUP_S3_REGION`,
   `BACKUP_S3_BUCKET`, `BACKUP_S3_ACCESS_KEY_ID`, `BACKUP_S3_SECRET_ACCESS_KEY`. По желанию —
   `BACKUP_S3_PREFIX`, `BACKUP_HOUR_MSK`, `BACKUP_RETENTION_DAYS`.
4. В «Системе» нажмите «Создать копию в хранилище» и убедитесь, что в журнале копий появилась успешная запись.

Хранилище оплачивается отдельно по тарифу провайдера; подключение — решение владельца.

### Восстановление

Команды запускаются с компьютера администратора, в копии репозитория после `npm ci`. Нужен тот же
`BACKUP_ENCRYPTION_KEY`, для S3 — переменные `BACKUP_S3_*`.

```bash
# список копий в хранилище
npm run db:backups
# копия в файл (из базы DATABASE_URL или --source <URL>)
npm run db:backup -- --out integro.bak
# восстановление в ОТДЕЛЬНУЮ проверочную базу
npm run db:restore -- --file integro.bak --target "postgresql://user:pass@host:5432/integro_check?sslmode=require"
npm run db:restore -- --s3-key integro-backups/2026-10-20T00-00-00Z.bak --target "<URL проверочной базы>"
```

Порядок действий:

1. **Всегда сначала восстанавливайте в отдельную пустую базу**, а не в рабочую. Утилита применяет
   миграции, очищает таблицы копии и загружает строки в одной транзакции. При любой ошибке всё
   откатывается.
2. Проверьте проверочную базу: число заявок, последние заявки, переписку. Для этого можно временно
   запустить сайт с `DATABASE_URL` проверочной базы.
3. Восстановление поверх рабочей базы (`--target` совпадает с `DATABASE_URL`) утилита выполняет только
   с флагом `--allow-production`. Делайте это осознанно: данные, появившиеся после копии, будут удалены.
   Перед этим остановите приложение и сделайте свежую копию.
4. Копия от более новой версии сайта (с неизвестными миграциями) не восстанавливается, пока не обновлён код.

**Что проверено.** Выгрузка, шифрование, восстановление в отдельную базу `integro_restore_test`,
совпадение данных, продолжение нумерации, откат повреждённой копии, отказ при неверном ключе и
защита от восстановления в рабочую базу без флага. Это проверено интеграционным тестом
(`tests/integration/crm-ops.test.ts`) и вручную через CLI. Работа с реальным S3-хранилищем **не
проверялась**: подпись запросов (SigV4) сверена с эталонным примером из документации AWS.

## 3. Мониторинг: раздел «Система и интеграции» (`/admin/sistema`)

- **Каналы.** MAX и Telegram: настроен ли канал, последний успешный приём и обработка события, последняя
  ошибка, очередь неотправленных сообщений. Данные берутся из базы; внешние API в обычном режиме не
  опрашиваются.
- **Проверка подключения.** Запросы `getMe` / `me` к API — раз в 30 минут фоном или по кнопке «Проверить
  подключение сейчас».
- **Уведомления.** Push настроен или нет, число подписок и получателей в Telegram, неуспешные доставки.
- **Резервные копии.** Настройки (без секретов), последние запуски, кнопки ручной копии и выгрузки.
- **Неуспешные операции.** Необработанные события мессенджеров, неотправленные сообщения и неуспешные
  доставки уведомлений — с кнопкой «Повторить».
- **Сроки хранения.** См. раздел 5.
- **Журнал** (`/admin/sistema/zhurnal`). Ошибки, повторы, дубли и сбои с фильтрами по каналу, результату и
  периоду. Тексты ошибок очищаются от строк, похожих на токены и секреты.

Повторы обработки событий мессенджеров идут с растущим интервалом: 1, 2, 4, 8 минут, всего 5 попыток.
После последней приходит уведомление «Ошибка обработки». Неотправленные ответы повторяются
автоматически, только если сообщение точно не ушло. При неизвестном результате нужно решение
оператора («Отправить ещё раз»).

Фоновые задачи (раз в минуту, `src/lib/ops/scheduler.ts`): досылка сообщений, доставка уведомлений,
автоматические сообщения ботов, ежедневная копия, раз в 30 минут — проверка интеграций, раз в сутки —
сроки хранения. Задачи рассчитаны на один экземпляр приложения: при нескольких экземплярах копия
защищена блокировкой в базе, а очереди — атомарным захватом строк.

## 4. Аналитика (`/admin/analitika`)

Все показатели считаются на сервере только из базы. Если знаменатель равен нулю, вместо 0 % показывается «—».

**Когорты**

- **Диалоги** — карточки MAX и Telegram с первым сообщением (`first_seen_at`) в периоде.
- **Заявки** — созданные в периоде (`created_at`).
- **Период** — календарные дни по Москве, обе границы включительно.

**Формулы**

- **Новые диалоги** — число диалогов когорты.
- **Уникальные клиенты в диалогах** — число различных людей: связанные вручную карточки
  (`person_id`) считаются одним человеком.
- **Уникальные телефоны в заявках** — число различных номеров. Заявки без телефона указаны отдельно:
  клиент для них не определяется.
- **Квалифицированный лид** — диалог с отметкой оператора «Квалифицированный лид» или с заявкой,
  плюс заявки без диалога (сайт, ручные).
- **Первичное обращение** — диалоги когорты плюс заявки без диалога.
- **Этап «дошла до…»** — заявка сейчас на этом этапе или дальше либо была на нём по истории изменений.
  Проигранная после переговоров заявка учитывается в «Переговорах».
- **Выиграно / проиграно** — текущий этап «Сделка выиграна» / «Сделка проиграна».
- **Конверсии.** «Диалог → заявка» = диалоги с заявкой / диалоги. «Обращение → заявка» = заявки /
  первичные обращения. «Заявка → выигранная сделка» = выигранные / все заявки. «Доля выигранных среди
  закрытых» = выигранные / (выигранные + проигранные).
- **Оплачено** — сумма «Оплачено» по заявкам со статусом оплаты «частично» или «полностью».
- **По договору** — сумма сделки по выигранным заявкам.
- **Средний чек** — сумма по договору / число выигранных заявок с суммой.
- **Валюты.** Суммы в разных валютах не складываются, итоги даются по каждой валюте.
- **Без ответа сейчас** — диалоги когорты, которые сейчас открыты и отмечены «нужен ответ».
- **Время до первого ответа оператора** — от первого сообщения клиента до первого доставленного
  ответа оператора. Показываются медиана и среднее. Ответы бота не считаются.
- **От первого контакта до заявки** — от первого сообщения в диалоге до создания заявки (только заявки из
  диалогов; для сайта момент первого контакта неизвестен).

**Фильтры**

- **Период и канал** применяются ко всему отчёту.
- **Услуга, этап, статус, ответственный, причина отказа, оплата** применяются только к заявкам: у диалога
  этих свойств нет. На странице это указано.

**Каналы**

- **WhatsApp, Авито, телефон, почта** — заявки, зарегистрированные вручную («Новая заявка»). Переписка
  WhatsApp в систему не поступает. Для кнопки WhatsApp на сайте есть только статистика переходов.
- **Авито** — будущий канал, пока только ручная регистрация.

**Атрибуция сайта.** Источник — UTM-метки, домен перехода и страница входа первого захода в вкладке
(sessionStorage). Они передаются только вместе с заявкой. Если данных нет — «Не определён».

**Выгрузка CSV.**

- «Показатели CSV» — все показатели с числителем и знаменателем.
- «Заявки CSV» — заявки с полями воронки, без имени, телефона, почты и текста обращения.
- Формат — UTF-8 с BOM, разделитель «;», значения, похожие на формулы, экранируются.

**Причины отказа** (`/admin/analitika/prichiny`) редактируются. Причина не удаляется, а отключается,
поэтому история и аналитика сохраняются.

**История заявки.** Создание, статус, этап, причина отказа, ответственный, канал, источник, суммы и оплата
записываются в `request_history` с отметкой, кто изменил: администратор, сайт или бот.

## 4а. План продаж (`/admin/plan-prodazh`)

**Направления.** Три направления хранятся в таблице `sales_directions`:

| Идентификатор | Название по умолчанию | Услуга, по которой новая заявка получает направление |
| --- | --- | --- |
| `ocenka` | Оценка | Оценочная деятельность |
| `sud_zaklyuchenie` | Судебное заключение | Экспертные исследования (заключение специалиста для судебных споров) |
| `sud_ekspertiza` | Судебная экспертиза | Судебная экспертиза |

- Названия меняются внизу страницы, в блоке «Направления». Данные и расчёты привязаны к идентификатору, а не к названию.
- Новая заявка с сайта, из бота или созданная вручную получает направление по услуге, которую выбрал клиент или оператор.
- Заявка без услуги направления не получает.
- Старые заявки автоматически не классифицировались. Направление выбирается вручную в карточке заявки, в блоке «Сделка», и записывается в историю заявки.
- Список заявок без направления: `/admin?direction=none` (ссылка «Классифицировать» на странице плана).

**Хранение.**
- Одна запись `sales_plans` на месяц и направление (уникальность «период + направление»).
- В записи хранятся:
  - план выручки, продаж и лидов;
  - ручные факты;
  - источник каждого факта: `auto` или `manual`.
- Пустое поле — «не заполнено», ноль — введённый ноль.
- Отклонения, средний чек, конверсии и итоги не хранятся — они вычисляются (`src/lib/sales-plan/calc.ts`), поэтому таблица и карточки не расходятся.

**Сохранение.**
- Кнопка «Сохранить» отправляет изменённые направления одним действием, в одной транзакции.
- Внизу экрана видны состояния: есть несохранённые изменения, сохранение, сохранено, ошибка с кнопкой «Повторить».
- Защита от потери данных: предупреждение при закрытии вкладки и при переходе на другой месяц с несохранёнными изменениями.
- Защита от перезаписи: у записи есть версия. Если значения изменили в другом окне, ничего не сохраняется, и предлагается «Загрузить актуальные» или «Сохранить мои поверх».
- Значения проверяются повторно на сервере: суммы и количества не могут быть отрицательными, количества — только целые. В базе стоят такие же ограничения.
- «Очистить значения месяца» удаляет запись направления за месяц после подтверждения.

**Автоматические факты** (источник «Авто из CRM», месяц по Москве):
- **Выручка.** Сумма поля «Получено» по заявкам направления:
  - статус оплаты «частично» или «полностью»;
  - дата поступления в месяце;
  - валюта RUB.
- **Продажи.** Число таких заявок: одна заявка — один заказ. Заявки без оплаты и сообщения продажами не считаются.
- **Лиды.** Уникальные клиенты с заявкой по направлению, созданной в месяце.
  - Клиент — это карточка мессенджера (связанные карточки считаются одним человеком), иначе телефон, иначе сама заявка.
  - Несколько обращений одного клиента в месяце — один лид.
  - На вкладке направления показана разбивка лидов по каналам: сайт, MAX, Telegram, ручные заявки из WhatsApp, Авито и других.
- **Что в автоматический факт не входит:**
  - заявки без направления — их число показано на странице;
  - оплаты без даты поступления и оплаты не в рублях — их число показано на вкладке направления.
- **Дата оплаты.** При сохранении оплаты в карточке заявки дата поступления теперь обязательна.
- **Ручной ввод.** Для любого факта можно выбрать «Вручную». Ручное значение сохраняется и при обратном переключении на «Авто».

**Ограничения автоматического подсчёта.**
- В заявке одно поле оплаты. Если оплата пришла частями в разные месяцы, вся сумма учитывается в месяце последней указанной даты поступления. Точный учёт потребует журнала платежей.
- Диалоги в мессенджерах без заявки не имеют направления, поэтому лидами по направлению не считаются (в разделе «Аналитика» они учитываются как обращения).

**Формулы:** см. `src/lib/sales-plan/calc.ts`.
- Отклонение — факт − план; для конверсии — в процентных пунктах.
- Выполнение — факт / план × 100.
- Средний чек — выручка / продажи.
- Конверсия — продажи / лиды × 100.
- **Итоги:**
  - выручка, продажи и лиды суммируются;
  - итоговый средний чек = сумма выручки / сумма продаж;
  - итоговая конверсия = сумма продаж / сумма лидов, а не среднее конверсий.
  - В итоговый средний чек и конверсию входят направления, где известны оба значения.
- При нулевом или пустом знаменателе выводится «—».

**История.**
- Сравнение с предыдущим месяцем.
- График фактической выручки за 12 месяцев по сохранённым планам и данным CRM: строится, только если данные есть.
- Направление с наибольшей выручкой; направление с лучшей конверсией, если конверсия известна хотя бы для двух направлений.

## 4б. Онлайн-чат на сайте («Веб-чат», `/admin/veb-chat`)

**Как устроен.** Веб-чат — третий канал общей системы обращений, рядом с MAX и Telegram (`channel = 'web'`).
Диалоги, сообщения, заметки, статусы, уведомления, связывание карточек, создание заявки из диалога и аналитика —
общие с ботами. Раздел «Веб-чат» показывает только диалоги этого канала; те же диалоги видны в «Обращениях».

**Посетитель.**
- Кнопка «Онлайн-консультант» в правом нижнем углу всех публичных страниц. Пока на экране уведомление о cookie, кнопка не показывается.
- В окне консультант называется «Анастасия». Приветствие — часть интерфейса и в базе не сохраняется.
- Диалог создаётся только при первом сообщении и только после отметки согласия на обработку ПД (редакция
  согласия сохраняется в карточке).
- **Сессия.**
  - Случайный токен в cookie `__Host-integro-chat`: HttpOnly, Secure, SameSite=Lax, 30 дней с последнего сообщения.
  - В базе хранится только SHA-256 токена.
  - Переписка восстанавливается в том же браузере; по номеру диалога доступа нет.
- **Отправка.**
  - Enter — отправить, Shift+Enter — новая строка.
  - Статусы «Отправляется…», «доставлено» (только после подтверждения сервером), «Не отправлено» с кнопками «Повторить» и «В поле ввода».
  - Повтор идёт с тем же ключом, поэтому дубля нет, даже если первая попытка сохранилась.
  - Черновик сохраняется в вкладке.

**Обновление в реальном времени — опрос сервера (polling).** Отдельный сервис и WebSocket не нужны,
это работает на текущем хостинге.
- Открытый виджет опрашивает сервер каждые 3 с, закрытый — каждые 25 с (для счётчика непрочитанных).
  В скрытой вкладке опрос на паузе; при ошибках интервал растёт до 30 с, а при восстановлении связи запрос идёт сразу.
- Курсор `after` + `since` возвращает и новые сообщения, и ответы, ставшие видимыми позже. Виджет отбрасывает
  дубли по id, поэтому после переподключения пропущенное приходит, а повторов нет.
- Админка: карточка диалога веб-чата обновляется каждые 3 с, список «Веб-чат» — каждые 5 с.

**«Анастасия печатает…»** — только по реальному сигналу. Поле ответа оператора в карточке веб-чата отправляет
отметку не чаще раза в 2,5 с, отметка живёт 6 с и снимается при очистке поля, уходе из него и отправке ответа.
В остальное время в окне — режим ответа из `company.contacts.workingHours` или «Диалог завершён».

**Оператор.**
- Список: имя (у гостя — «Посетитель сайта № N»), «гость», число непрочитанных, «● в чате» (виджет был
  активен в последнюю минуту), последнее сообщение, статусы.
- Фильтры: все, новые (оператор ещё не отвечал), ждут ответа, ждут клиента, в работе, закрытые. Поиск — по тексту сообщений.
- Открытие карточки отмечает входящие прочитанными.
- У ответов видна отметка «Показано посетителю · прочитано».
- Посетителю ответы показываются от имени «Анастасия», в истории хранится фактический автор — «Оператор».
  Учётная запись администратора одна, поэтому конкретный сотрудник не различается.
- Внутренние заметки хранятся отдельно (`chat_notes`) и посетителю никогда не передаются.
- Закрытие диалога видно посетителю. Новое сообщение посетителя открывает диалог снова; опрос после закрытия в веб-чате не отправляется.

**Уведомления.** Те же типы, что и для ботов: «Новое сообщение · Веб-чат» (не чаще раза в 15 мин по диалогу) и
«Нужен ответ · Веб-чат» — в центр уведомлений, push и Telegram сотрудникам по настройкам. Текст сообщения во
внешние каналы не передаётся. Сообщения из Telegram и MAX в веб-чат не пересылаются.

**Защита.**
- POST-запросы принимаются только с этого сайта (Origin) и только в формате JSON.
- Сообщение — не длиннее 2000 символов, управляющие символы удаляются, текст выводится как текст (без HTML).
- Лимиты (в памяти процесса, окно 14 мин):
  - 60 сообщений с одного IP;
  - 5 новых диалогов с одного IP;
  - 2000 запросов обновлений с одного IP.
- API админки (`/api/admin/webchat/typing`) — только для вошедшего администратора.

**API.**
- `GET /api/webchat` — обновления: `?after=&since=` или `?before=` для истории.
- `POST /api/webchat/messages` — сообщение посетителя.
- `POST /api/webchat/read` — посетитель прочитал ответы.
- `POST /api/admin/webchat/typing` — оператор печатает.

## 5. Безопасность и персональные данные

**Результаты аудита**

- **Доступ.** Каждая страница, серверное действие и API админки проверяет сессию на сервере
  (`requireAdminPage` / `requireAdmin` / `isAdmin`). Без сессии API отвечает 401, а страница
  перенаправляет на вход; это проверено e2e-тестом. Роль одна — администратор: разграничения прав между
  сотрудниками нет, поэтому IDOR между пользователями невозможен. Идентификаторы в адресах проверяются
  по формату.
- **CSRF.** Серверные действия Next.js сверяют `Origin` с хостом. POST-API (`/api/admin/push`,
  `/api/admin/backup`) дополнительно проверяют тот же источник. Cookie сессии — `HttpOnly`, `Secure`,
  `SameSite=Lax`, префикс `__Host-`.
- **Частота запросов.**
  - Вход: ограничение попыток в базе.
  - Форма заявки: в памяти процесса.
  - Webhook мессенджеров: проверка секрета и защита от повторной доставки.
  - Ручная резервная копия: не чаще раза в 5 минут.
- **Секреты.** Только в переменных окружения. Тексты ошибок в журнале очищаются от токенов.
- **CSV.** Защита от формульной инъекции во всех выгрузках.
- **Минимизация ПДн.** Push и Telegram — без ПДн. Выгрузка аналитики — без ПДн. В резервную копию не
  входят сессии.

**Сроки хранения** (раздел «Система»)

- **Служебные записи** очищаются всегда: уведомления — 90 дней, журнал — 180 дней, журнал копий — 365 дней.
- **Закрытые диалоги и завершённые / отклонённые заявки** удаляются, только если владелец задал срок
  (от 30 дней). По умолчанию срок не задан: решение принимает оператор ПДн.
- **Черновик ответа оператора** хранится в sessionStorage вкладки администратора и стирается при
  закрытии вкладки или после отправки.

## 6. Ограничения

- Одна учётная запись администратора, без ролей и журналирования действий по сотрудникам. Поле
  «Ответственный» — текст.
- Обновление центра уведомлений — опросом каждые 20 секунд, а не мгновенно. Push приходит сразу, если
  настроен.
- Ограничение частоты формы хранится в памяти процесса и рассчитано на один экземпляр приложения.
- Реальная доставка push и Telegram-уведомлений сотрудникам, а также работа с реальным S3 в тестах
  имитировались. После настройки на сервере проверьте их кнопкой «Отправить тестовое уведомление» и
  «Создать копию в хранилище».
